# 사진 비율 — 커스텀 카메라 뷰파인더 vs 피드 3:4 크롭

## 문제

- 상태: accepted
- 기록일: 2026-09-23

- 피드 게시물 사진: **3:4** 고정 (`FEED_IMAGE_WIDTH`/`HEIGHT` = 786:1048, `cropImageBlobToAspectRatio`로 업로드 시 강제 크롭)
- 커스텀 카메라 뷰파인더(`CameraView.tsx`): `h-full w-full object-cover`로 **기기 화면 전체**를 채움 (iPhone 기준 약 19.5:9, 3:4보다 훨씬 좁고 긴 비율)
- 두 비율이 달라서, **촬영 중 화면에 안 보이던 좌우 영역이 최종 3:4 크롭 사진엔 들어가는 현상** 발생. 촬영자가 프레이밍한 것과 실제 저장되는 사진이 다름
- 웹 폴백 카메라(`useCameraCapture.ts`)와 iOS 네이티브 카메라(`useNativeCamera.ts`, `NativeCameraPlugin.swift`) 둘 다 동일 구조라 같은 문제

## 원인

- 상태: accepted
- 기록일: 2026-09-23

- 화면 비율(≈19.5:9, 좁고 긴 형태)이 출력 비율(3:4, 상대적으로 넓은 형태)보다 **더 좁음**
- 최종 사진이 화면보다 넓은 비율이라는 건, 화면에 안 보이던 좌우를 반드시 채워 넣어야만 3:4가 나온다는 뜻 → **뷰파인더가 화면 전체를 채우는 한 피할 수 없는 결과**. 코드 버그가 아니라 두 요구사항(풀스크린 뷰파인더 + 고정 3:4 출력) 사이의 구조적 트레이드오프

## 검토한 선택지

- 상태: proposed
- 기록일: 2026-07-09

1. **뷰파인더를 3:4로 박스 처리** — 화면 안 채우고 레터박스, WYSIWYG 보장. 풀스크린 몰입감 포기
2. **최종 출력을 화면 비율(풀스크린)에 맞춤** — 화면은 그대로 두지만 앱 전체(그리드/상세) 사진 비율 컨벤션을 바꿔야 함
3. **Instagram식 "Hug height" — 피드가 사진 원본 비율에 맞춰 가변 높이** (2026-07-09 팀 논의, 경준/이시언)
   - 장점: 촬영한 그대로 저장·표시, 위 문제 자체가 해소됨
   - **실제 손대야 하는 범위** (조사 결과):
     - 안 건드려도 됨: 그리드/리스트 썸네일(이미 정사각형 고정), 스티커·핀 위치(이미 %기반이라 가변 비율에도 호환)
     - 손대야 함: 업로드 파이프라인 전체(`cropImageBlobToAspectRatio`, `composePhoto.ts`, `useCameraCapture.ts`, `useNativeCamera.ts`가 지금 무조건 3:4로 강제 크롭 중), 상세 프레임(`FeedImageDetail.tsx`의 `fit` 로직은 고정 높이 안에서 contain/cover만 전환하는 것이라 진짜 가변 높이와는 다름 — 프레임 높이 자체를 가변으로 바꿔야 함), 캐러셀(`FeedImageCarousel.tsx`, 슬라이드마다 높이 다를 때 스와이프 시 컨테이너 높이 전환이 기술적으로 까다로움)
     - 디자인 결정 필요: 최소/최대 비율 제한(인스타도 스팸성 극단 비율 방지용으로 제한 둠), 카메라 리뷰 화면(`aspect-3/4` 박스)도 가변으로 갈지 여부

## 현재 상태: 보류

- 상태: rejected
- 기록일: 2026-07-09

지금 당장 구현하지 않음. 3번(Hug height)이 근본적으로 제일 깔끔한 해결책이지만, 카메라 캡처 파이프라인 + 상세/캐러셀 두 덩어리에 걸친 멀티 파일 작업이라 하루이틀 규모가 아님. 구현 전에 디자인 쪽에서 최소/최대 비율 스펙부터 정해야 순서가 맞음.

- 팀 논의 원문(2026-07-09): "피드를 16:9로 바꾸면 해결될까요?" → "그러면 대공사가 좀 있을 것 같은데" → "이미지 프레임 height를 Hug로 해서 인스타처럼 업로드/촬영한 이미지에 맞게 피드 길이가 설정되게 하는 것은 어려울까요?"
- 재검토 시점: 디자인팀에서 최소/최대 비율 스펙 확정되면, 또는 카메라 UX 개선이 우선순위에 오르면
